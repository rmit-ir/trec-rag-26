1. **§2.2 still creates a serious recall failure mode.** Keeping `adjacent_not_relevant` only protects the judge category most explicitly recognized as uncertain; it does nothing for useful documents the judge confidently but incorrectly labels `irrelevant`. Given facets_agent’s known under-decomposition, a document relevant to an unstated implicit sub-requirement is especially likely to look irrelevant against the narrow, current `requirement` string.

2. **The filter bakes the agent’s existing failure mode into the retrieval gate.** The requirement passed to the judge is authored by the same agent that fails to identify implicit requirements; judging relevance solely against that requirement can suppress evidence for exactly the missing facets the final answer should have covered. “Requirement missing” fail-open is not enough: a present but incomplete requirement is the dangerous case.

3. **§3 does not actually measure evidence recall.** Rubric scores and criterion tallies are downstream, noisy outcome measures; they cannot tell whether a filtered document was necessary evidence, whether the agent failed to search for it later, or whether a score drop is ordinary run/judge variance. Before shipping a mandatory suppressor, the plan needs a direct counterfactual audit: identify documents filtered in the treatment that were used, cited, or materially relevant in the baseline/replay, ideally per requirement and especially for implicit criteria.

4. **“Revert if recall regresses on any topic” is both underspecified and not statistically credible.** A single-topic score movement on a 30-topic set may be grader or generation variance, while aggregate non-regression can still conceal systematic losses on important requirements. Define paired-run methodology, generation/grading controls, acceptable degradation thresholds, and a minimum evidence-recall threshold before looking at results.

5. **The four-topic gate in §3/§5 is far too weak for this specific risk.** Hand-inspecting filtered documents on one topic can catch parser failures, but it will not expose category-specific false negatives, topic-distribution failures, or failures on implicit requirements. The gate should deliberately include topics where baseline worklogs show missed implicit facets and inspect *all* dropped documents against a requirement/evidence rubric, not merely one convenient sample.

6. **§0 does not justify the causal claim that filtering will free effort for decomposition and synthesis.** The data show more rejected documents and higher peak context, but not that manual triage is what prevented decomposition, nor that saved context/tokens become additional planning or more specific writing under the current prompts, turn limits, and stopping policy. The filter may simply replace model triage with judge latency and cause the agent to issue more searches, leaving the actual decomposition behavior unchanged.

7. **The “rejected documents” finding weakens the proposed mechanism rather than proving it.** Per §0, rejected documents are compacted after one turn and do not persist; therefore the durable-context explanation is already excluded, while the claimed transient “effort budget” cost remains unmeasured. The plan should measure turns spent on search/triage, tool-call count, model completion tokens, time-to-final, and explicit requirement coverage before asserting that filtering changes the relevant budget.

8. **A one-call batch judge per search has unaddressed quality and capacity risks.** Search calls may return enough text that the judge prompt must truncate, reorder, or compress documents, causing verdicts to depend on position and batch composition rather than relevance. The plan needs explicit maximum batch sizes, stable document IDs, truncation policy, overflow behavior that fails open, and tests for verdict/document alignment.

9. **The proposed interface is too permissive for a mandatory data-path transformation.** `SearchFilterResult(kept: list[dict], ...)` allows a filter to reorder, duplicate, mutate, fabricate, or substitute documents unless the harness validates that `kept` is an ordered subset of the original result IDs. The API should return kept document identifiers or a boolean mask, and the harness should compute `filtered_count` itself rather than trusting filter-provided accounting.

10. **Fail-open on exceptions is necessary but insufficient operationally.** Swallowing judge errors without prominent telemetry can turn an outage, timeout misconfiguration, malformed-response spike, or batch-limit regression into silently inconsistent behavior across topics. Record filter status, latency, judge model/version, raw verdict counts, fallback reason, and whether every original document was preserved; otherwise the evaluation cannot distinguish a real treatment from partial bypass.

11. **The transparency line in §2.1 does not provide meaningful recovery.** Telling the model that “N of M” results were filtered does not reveal what was removed or let it reconsider a particular item; it can only issue another vague search, potentially consuming more budget. If this is retained, expose a bounded recovery mechanism—e.g., an opt-in `show_filtered_results`/“retrieve discarded candidates” path or a soft-ranked list—so the main model can override the judge when a requirement appears under-evidenced.

12. **The plan adds a latency cost to every search without showing that search latency is non-binding.** At roughly 18 searches per topic, sequential judge calls can materially increase end-to-end time and may hit judge-service concurrency/rate limits when tool calls are parallelized. “Cheap in dollars” is not an adequate capacity analysis; benchmark p50/p95 added latency, timeout behavior, and contention with existing `judge_relevance` and RAGDoll workloads.

13. **A simpler approach better matches §0: improve planning and prioritization without irreversible suppression.** Use the existing judge machinery to attach relevance labels/scores or rank results, then let the main model see the top items plus a compact inventory of lower-ranked candidates; alternatively, enforce an up-front implicit-requirement checklist and reserve turns/tokens for per-requirement evidence gathering and final specificity checks. That directly targets the measured decomposition/synthesis loss while preserving the additional retrieval freedom that was deliberately given to facets_agent.

14. **If any filtering is attempted, start with only demonstrably low-value cases, not semantic “irrelevant” judgments.** Exact duplicates, empty/boilerplate pages, malformed results, or repeated documents already seen under the same requirement are substantially safer candidates for hard removal. Semantic relevance filtering should remain advisory until direct evidence-recall evaluation demonstrates that its false-negative rate is acceptably low on implicit requirements.

**Verdict: proceed with changes.**
