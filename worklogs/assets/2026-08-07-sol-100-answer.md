## Decision: build a four-candidate, winner-take-all selector

Implement a lightweight **best-of-4 complete-trajectory ensemble**, analogous only at the mechanism level to `ensemble_select.py`.

Do **not** build `candidate_union` under this budget. Its item extraction, coverage accounting, budget reconciliation, and fallback semantics create too much implementation and debugging risk for a $100 experiment. Winner selection is much more likely to produce a clean, interpretable result today.

### Exact mechanism

For each of the same 15 topics:

1. Treat the existing frozen base-cell answer as Candidate A.
2. Run **three fresh, independent copies of the complete base pipeline** as Candidates B–D:
   - identical base-cell configuration;
   - same model and prompts;
   - same source inputs;
   - normal sampling variance only;
   - brief/main/review stages rerun independently rather than sharing a brief.
3. Randomize candidate order and labels before selection.
4. Make one `gpt-5.6-sol` selector call containing:
   - the original request;
   - all four answers verbatim;
   - instructions to construct a request-specific 10–16-criterion rubric internally;
   - criterion-level candidate assessments;
   - a required winner ID.
5. Return the winning candidate **unchanged**. No rewriting, merging, citation repair, or union.
6. On malformed output, unknown ID, context overflow, or other protocol failure, fall back to Candidate A and log the failure.

Using the existing base answer as one candidate makes the experiment exactly paired to the current control and saves one new trajectory per topic. A production configuration would generate all four candidates fresh.

### Call multiplier

This adds, per topic:

- **+3 complete base trajectories**
- **+1 selector call**

If a complete trajectory currently uses two model calls, this is **+7 calls/topic**. If brief, main, and review are three separate calls, it is **+10 calls/topic**.

The generation portion is approximately 4× base inference cost in production. For this experiment, reusing the frozen base answer means paying for only 3× new generation plus selection.

---

## Why this mechanism

The prior search already showed that local prompt/harness changes have little remaining headroom. Best-of-N attacks a different limitation: **within-configuration outcome variance**. It can help when the base model is capable of a better answer but does not produce it reliably in one trajectory.

It also provides a decisive diagnostic:

- If the candidate pool contains materially better answers and the selector finds them, ensemble selection is promising.
- If candidates are nearly identical, there is no diversity headroom.
- If better candidates exist but selection does not outperform a random candidate, the selector is the bottleneck.
- If even the candidate-pool oracle has no improvement, further ensemble work—including `candidate_union`—is unlikely to justify its complexity.

## Control and experimental discipline

Use the exact existing 15-topic manifest and frozen base artifacts.

Keep constant:

- model versions;
- base prompts and structure;
- source corpus/fetch results;
- answer token budget;
- brief/main/review configuration;
- standalone rubric script and judge configuration.

Only the following factor changes:

> Produce three additional independent complete trajectories and select one answer from those plus the frozen base answer.

Additional safeguards:

- Give the base answer no privileged “anchor” label.
- Randomize candidate order deterministically from topic ID.
- Log candidate hashes, order, selector rubric/scores, winner, costs, and fallback reason.
- Do not truncate candidates for the selector. Fail to Candidate A instead.
- Check exact/near-duplicate rates. If more than roughly 20% of fresh candidates are duplicates, flag inadequate sampling diversity; do not silently change prompts.
- Do not give the selector source material unavailable to the base generator or allow tool use. This remains answer selection, not an extra research/revision stage.

## Promotion bar

### Standalone gate

Keep the previously established threshold:

- **Promote at ≥2.400/3**, i.e. at least **+0.133** over 2.267.
- This corresponds to a net gain of two rubric points over the 15-topic set.
- The selected cell should also outperform the predeclared raw fresh-candidate row; otherwise the observed improvement cannot confidently be attributed to selection.

Record paired topic-level changes, not only the mean:

- improved;
- unchanged;
- regressed;
- whether regressions involve factual/citation failures.

A score of 2.333 or below is “no measurable standalone movement” under the established threshold.

### Arena gate

If standalone reaches 2.400, run the same 30-comparison arena protocol against `aus_agent_v2`.

Operational interpretation:

- **≥45% scored win rate**: worth the $100 as meaningful gap closure.
  - With no ties, this means at least 14/30 wins, versus the base’s 12/30.
- **≥50%**: strong promotion result.
- **40–43%**: no demonstrated arena improvement.
- Below 40%: reject even if standalone improved.

A 30-match arena result is directional rather than statistically conclusive, so retain the raw decisions and ties. The goal here is a promotion signal, not a high-confidence population estimate.

### What counts as useful even without promotion

The experiment is still informative if it establishes one of these clearly:

- meaningful candidate-pool oracle headroom but weak selector performance;
- selector uplift over a random fresh trajectory without reaching 2.400;
- insufficient candidate diversity under the current sampling setup;
- no oracle headroom, strongly arguing against spending on `candidate_union`.

## Implementation location and harness reuse

Nothing in the five tested generic `agent_harness` toggles appears to provide complete-trajectory branching and winner selection. Unless repository inspection reveals an untested generic best-of-N primitive, this should be a **small new orchestration layer in `brief_revise_agent`**, not a new shared-harness feature.

Reuse:

- the existing function that runs one complete base trajectory;
- the shared model-call/client wrapper;
- existing token/cost logging;
- cached frozen base outputs;
- `score_one()` / `standalone_rubric_score.py`;
- existing arena runner.

Before adding code, search for reusable plumbing:

```bash
rg -n "ensemble_select|candidate_union|best.of|num_candidates|candidate.*select|parallel.*candidate" \
  agent_harness brief_revise_agent
```

If `agent_harness` can already execute multiple isolated runs or fan out calls, use that execution plumbing. Do not broaden this experiment into a generic harness redesign.

Suggested interface:

```text
--ensemble-select
--candidate-count 4
--seed-candidate-manifest <existing-base-outputs>
--fresh-candidates 3
--selector-model gpt-5.6-sol
```

The implementation should primarily be:

1. run/cache three additional trajectories;
2. serialize and randomize four candidates;
3. issue one selector call;
4. validate winner ID;
5. copy the winning answer verbatim;
6. emit a complete audit record.

This is genuinely distinct from all prior tested factors while remaining small enough to implement, meter, and evaluate within the new $100 cap.
